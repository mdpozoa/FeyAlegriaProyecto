Introducción y Marco Conceptual

¿Qué es cada técnica y cuándo se usa?

Esta práctica aplica tres metodologías de análisis de seguridad sobre el proyecto SafeCampus Monitor: una aplicación web con frontend en Vue.js 3, backend en Node.js + Express y base de datos SQLite, desplegada en Vercel.

Técnica SAST — Estático DAST — Dinámico IAST — Interactivo
¿Qué analiza?El código fuente sin ejecutarloLa aplicación en ejecución desde afueraLa aplicación por dentro durante la ejecución
¿Cuándo actúa?Antes de compilar o desplegarCuando la app ya está corriendoMientras el QA/usuario navega la app
¿Quién lo hace?El desarrollador desde el IDEUn escáner externo (proxy/bot)Un agente instrumentado en el runtime
Ventaja claveDetecta errores de programación tempranoEncuentra vulnerabilidades reales en producciónCombina precisión de SAST con contexto de DAST
LimitaciónNo ve errores de runtimePuede dar falsos positivos, no ve el códigoRequiere agentes en el servidor (más complejo)
Herramienta usadanpm audit + Semgrep + ESLintOWASP ZAP + DevTools ChromeContrast CE + DevTools Network Inspector
🎯
Objetivo de la prácticaEjecutar las tres fases sobre SafeCampus Monitor, documentar los hallazgos de cada técnica, comparar sus resultados y redactar conclusiones sobre las vulnerabilidades encontradas y su remediación.

Navegador y Entorno Requerido

Configura tu espacio de trabajo antes de comenzar

Antes de iniciar cualquier fase, asegúrate de tener el entorno correcto. Cada técnica requiere herramientas específicas.

🖥️ Navegador recomendado:

🟢
✓ Recomendado Principal
Google Chrome
Tiene las DevTools más completas: Network, Security, Application (LocalStorage), Console y Lighthouse. Compatible con todas las extensiones de seguridad. Usa este para la mayoría de la práctica.
🦊
Mozilla Firefox
Excelente para DAST con OWASP ZAP porque configura el proxy más fácilmente. Usa Firefox cuando configures ZAP como proxy de interceptación.
🔵
MS Edge
Alternativa a Chrome si no tienes acceso. Mismo motor Chromium, DevTools equivalentes. Sirve como respaldo.
⚠️
No usar para las pruebas de seguridad: Internet Explorer, Safari o navegadores integrados en IDEs. No tienen las herramientas necesarias para interceptar tráfico ni inspeccionar correctamente las peticiones HTTP.

🛠️ Software que debes instalar antes de empezar:

  • Node.js LTS (v20+) — nodejs.org — Para ejecutar npm audit, instalar dependencias y levantar el servidor local.
  • OWASP ZAP 2.15+ — zaproxy.org — Herramienta DAST gratuita con interfaz gráfica. La más usada en la industria para pruebas de penetración web.
  • Semgrep CLI — semgrep.dev — Analizador estático de código fuente con reglas de seguridad para JavaScript/Vue.js.
  • Git Bash o PowerShell — Para ejecutar comandos en la terminal.
  • Extensión Chrome: "EditThisCookie" — Para manipular cookies durante DAST manual.
  • Extensión Chrome: "FoxyProxy" — Para enrutar el tráfico a través de ZAP sin cambiar la configuración del sistema.
Fase 1

🔵 SAST — Static Application Security Testing

Análisis del código fuente de SafeCampus Monitor sin ejecutar la aplicación. Usaremos tres herramientas complementarias: npm audit, Semgrep y ESLint Security Plugin.

📦
Herramienta 1 — npm audit
Gratuito CLI

npm audit analiza el archivo package.json y el árbol de dependencias buscando vulnerabilidades conocidas registradas en la base de datos pública del NIST (CVE).

1
Abre la terminal en la carpeta del proyecto
En Windows, haz clic derecho sobre la carpeta EmprendimientoProyectoFull y selecciona "Abrir en Terminal" o usa PowerShell.
Terminal
# Navega a la carpeta raíz del proyecto cd "C:\Users\mateo\OneDrive - Pontificia Universidad Católica del Ecuador\Desktop\EmprendimientoProyectoFull"
2
Ejecuta npm audit para el frontend
Este comando escanea las dependencias del frontend (Vue, Vite, Leaflet, Pinia, vue-router) y muestra vulnerabilidades por severidad.
Terminal
npm audit # Para ver el reporte completo en formato JSON (más detallado): npm audit --json > sast_npm_audit_report.json
3
Analiza los paquetes del servidor (backend)
El directorio server/ tiene su propio set de dependencias (Express, CORS, SQLite). Analízalas por separado.
Terminal
# Si hay un package.json en /server, entra a esa carpeta primero: npm audit --prefix ./server # Si no tiene su propio package.json, instala las deps del servidor: npm install express cors better-sqlite3 npm audit
4
Documenta los hallazgos en la tabla de resultados
Copia la salida del comando. Busca líneas que digan HIGH, MODERATE o LOW. Apunta: nombre del paquete, versión vulnerable, CVE y solución.
✅
Qué buscar en la salida: líneas como "found N vulnerabilities (X moderate, Y high)". Si dice "found 0 vulnerabilities", es un hallazgo positivo: ¡documenta que las dependencias están actualizadas!
🔍
Herramienta 2 — Semgrep (Análisis de Código Fuente)
Gratuito CLI

Semgrep analiza el código fuente línea por línea usando patrones de seguridad predefinidos. Detecta problemas como: inyección de datos, uso inseguro de eval(), manejo incorrecto de tokens, secretos expuestos en el código, etc.

ℹ️
Instalación de Semgrep: Requiere Python 3.8+. Si no tienes Python, descarga el ejecutable standalone desde semgrep.dev/docs/getting-started
1
Instala Semgrep
PowerShell / Terminal
# Opción 1: Con pip (Python requerido) pip install semgrep # Opción 2: Con winget (Windows Package Manager) winget install Semgrep.Semgrep # Verifica instalación: semgrep --version
2
Ejecuta el análisis SAST sobre el directorio src/
Usa el conjunto de reglas oficiales de seguridad para JavaScript. Analiza todos los archivos .js y .vue del proyecto.
Terminal
# Análisis con reglas de seguridad para JavaScript semgrep --config p/javascript ./src # Análisis con reglas específicas de OWASP Top 10 semgrep --config p/owasp-top-ten ./src # Análisis del servidor backend (Node.js) semgrep --config p/nodejs ./server # Guardar reporte completo en JSON semgrep --config p/javascript ./src --json > sast_semgrep_report.json
3
Analiza hallazgos específicos de SafeCampus
Semgrep revisará patrones peligrosos en tu código. Presta atención a estos archivos críticos del proyecto:
  • server/index.js — Verifica si las rutas de la API validan correctamente los datos de entrada (SQL Injection, missing auth).
  • src/stores/authStore.js — Revisa si el token JWT simulado se almacena de forma segura y si hay credenciales hardcodeadas.
  • src/controllers/IncidentController.js — Chequea si las coordenadas y datos del incidente se sanitizan antes de enviarse.
  • src/views/StudentView.vue — Verifica si los datos del formulario se escapan correctamente antes de renderizarse (XSS).
4
Hallazgo esperado crítico — Credenciales Hardcodeadas
Semgrep detectará que en authStore.js y en server/index.js las contraseñas están escritas directamente en el código. Esto es una vulnerabilidad de tipo A07:2021 – Identification and Authentication Failures según OWASP.
🚨
Vulnerabilidad detectada (SAST): Credenciales en texto plano dentro del código fuente. Líneas password === 'Estudiante123' y password === 'AdminSeguridad123' son comparaciones directas sin hashing (bcrypt/argon2). En producción, esto debe usarse con bcrypt.compare().
✏️
Herramienta 3 — ESLint con Plugin de Seguridad
Gratuito CLI

ESLint es el linter estándar de JavaScript. El plugin eslint-plugin-security agrega reglas específicas para detectar vulnerabilidades comunes en JavaScript.

1
Instala ESLint y el plugin de seguridad
Terminal
npm install --save-dev eslint eslint-plugin-security eslint-plugin-vue
2
Crea el archivo de configuración .eslintrc.json
Crea este archivo en la raíz del proyecto:
Archivo: .eslintrc.json
{ "env": { "browser": true, "es2021": true, "node": true }, "plugins": ["security", "vue"], "extends": [ "plugin:security/recommended", "plugin:vue/vue3-recommended" ], "rules": { "security/detect-object-injection": "warn", "security/detect-non-literal-regexp": "warn", "security/detect-possible-timing-attacks": "error", "security/detect-unsafe-regex": "error" } }
3
Ejecuta el análisis
Terminal
# Analiza toda la carpeta src/ npx eslint ./src --ext .js,.vue # Analiza el servidor npx eslint ./server --ext .js # Guarda el reporte npx eslint ./src -f json > sast_eslint_report.json

Fase 2

🔴 DAST — Dynamic Application Security Testing

Análisis de la aplicación en tiempo de ejecución. Levantaremos el servidor local y usaremos OWASP ZAP para interceptar, analizar y atacar la aplicación como lo haría un atacante externo.

⚠️
Importante antes de empezar DAST: Debes tener la aplicación corriendo localmente. Nunca ejecutes pruebas DAST contra el servidor de producción (Vercel) sin autorización explícita. Usa siempre http://localhost:5173 para estas pruebas.
⚡
Herramienta Principal — OWASP ZAP 2.15
Gratuito y Open Source Interfaz Gráfica

OWASP ZAP (Zed Attack Proxy) es la herramienta DAST más usada en la industria. Funciona como un proxy entre el navegador y el servidor, interceptando y analizando todo el tráfico HTTP/HTTPS.

1
Levanta la aplicación SafeCampus localmente
Abre dos terminales separadas: una para el frontend (Vite) y otra para el backend (Express + SQLite).
Terminal 1 — Frontend (Vue.js)
npm run dev # La app estará en: http://localhost:5173
Terminal 2 — Backend (Node.js)
node server/index.js # El servidor API estará en: http://localhost:3000
✅
Verifica que puedas abrir http://localhost:5173 en Chrome y ver la pantalla de login de SafeCampus antes de continuar.
2
Descarga e instala OWASP ZAP
Ve a zaproxy.org → Downloads → descarga la versión para Windows (.exe). Instala normalmente.
ℹ️
Primera vez que abres ZAP: Selecciona "No, I do not want to persist this session" para empezar limpio. Si te pregunta por el certificado CA, acéptalo (lo necesitarás para HTTPS).
3
Configura ZAP como proxy en Firefox
Para que ZAP intercepte el tráfico, configura Firefox para que use ZAP como proxy. ZAP por defecto escucha en el puerto 8080.
En Firefox:
1. Menú (☰) → Ajustes → buscar "proxy" → Configuración de red
2. Selecciona "Configuración manual del proxy"
3. HTTP Proxy: 127.0.0.1 · Puerto: 8080
4. Marca "Usar este proxy para HTTPS también"
5. Clic en Aceptar

O en Chrome con FoxyProxy:
1. Instala la extensión FoxyProxy en Chrome
2. Agrega un proxy: Host 127.0.0.1, Puerto 8080
3. Actívalo antes de navegar a localhost:5173
4
Navega la aplicación con el proxy activo (Spidering)
Con Firefox (proxy configurado), navega manualmente por toda la aplicación:
  • Abre http://localhost:5173
  • Haz login con el perfil de Estudiante
  • Activa el modo de reporte, haz clic en el mapa, envía un incidente
  • Cierra sesión → entra como Autoridad
  • Revisa el dashboard, haz clic en "Ver Detalles" de un incidente
  • Haz clic en "Exportar para Policía Nacional"
ZAP irá capturando automáticamente todas las peticiones en el panel "History".
5
Ejecuta el Escaneo Activo (Active Scan)
El Active Scan prueba automáticamente vulnerabilidades como XSS, SQL Injection, Path Traversal, etc.
En ZAP:
1. En el panel "Sites" verás http://localhost:5173 y http://localhost:3000
2. Clic derecho sobre localhost:3000 → "Attack" → "Active Scan"
3. Deja la configuración por defecto → clic en "Start Scan"
4. Espera a que complete (puede tardar 5–15 minutos)
5. Ve al tab "Alerts" para ver los hallazgos
6
Prueba manual de inyección SQL en la API
El endpoint POST /api/auth/login del servidor recibe email y password. Prueba manualmente si es vulnerable a SQL Injection usando ZAP.
🧪
Prueba de SQL Injection (solo en entorno local):
En ZAP → intercepta la petición POST /api/auth/login
Modifica el campo email con: ' OR '1'='1
Envía la petición y observa la respuesta del servidor.
Si responde con datos de usuario sin credenciales válidas → VULNERABILIDAD CONFIRMADA.
Si responde con 401 → el servidor valida correctamente.
7
Prueba manual de XSS en los campos del formulario
El campo "Descripción del Suceso" del formulario de reporte acepta texto libre. Prueba si acepta scripts.
En el formulario de reporte de estudiante:
1. Activa el modo de selección del mapa
2. Selecciona "Tipo: Otros"
3. En el campo descripción escribe: <script>alert('XSS')</script>
4. Envía el reporte
5. Ve al panel de Autoridad a ver la tabla de incidentes y haz clic en "Ver Detalles"

Resultado esperado: Vue.js escapa automáticamente el HTML, por lo que NO debe ejecutarse el script. Si lo hace → XSS confirmado.
8
Genera y guarda el reporte de ZAP
Exporta los resultados para incluirlos en la práctica.
En ZAP:
1. Menú → "Report" → "Generate Report"
2. Selecciona formato HTML o PDF
3. Guarda como dast_zap_report.html en la carpeta del proyecto
4. También puedes exportar desde "Alerts" → clic derecho → "Export Selected Alerts as HTML"
🔧
Herramienta Complementaria — Chrome DevTools (Manual)
Incluido en Chrome Interfaz Gráfica

Las DevTools de Chrome permiten hacer inspección manual de seguridad: revisar cookies, headers HTTP, almacenamiento local y el panel de Seguridad.

1
Abre Chrome DevTools en SafeCampus
Con la app abierta en localhost:5173, presiona F12 o clic derecho → "Inspeccionar".
2
Inspecciona el almacenamiento del token (Application Tab)
Ve al tab Application → Storage → Local Storage → http://localhost:5173. Verás las claves token y user guardadas en texto plano.
🚨
Hallazgo DAST: El token JWT y los datos del usuario se almacenan en localStorage, que es accesible por cualquier script JavaScript de la página. Esto lo hace vulnerable a ataques XSS. En producción se debería usar HttpOnly cookies.
3
Revisa los headers de seguridad HTTP (Network Tab)
Ve al tab Network → recarga la página → haz clic en cualquier petición → Headers → Response Headers.
Headers que deberían estar presentes (pero probablemente falten):
• Content-Security-Policy — Previene XSS
• X-Frame-Options: DENY — Previene clickjacking
• Strict-Transport-Security — Fuerza HTTPS
• X-Content-Type-Options: nosniff — Previene MIME sniffing

Si no aparecen → Hallazgo: Security Headers Faltantes (A05:2021)
4
Ejecuta Lighthouse Security Audit
Lighthouse es la herramienta de auditoría integrada en Chrome.
En DevTools:
1. Tab "Lighthouse" → selecciona categorías → marca "Best Practices"
2. Clic en "Analyze page load"
3. Revisa la sección de advertencias de seguridad en el reporte
4. Exporta el resultado como HTML o JSON para incluirlo en la práctica

Fase 3

🟣 IAST — Interactive Application Security Testing

El IAST combina lo mejor de SAST y DAST: instrumenta la aplicación en tiempo de ejecución para detectar vulnerabilidades reales con contexto completo. Para Node.js/Vue.js usaremos Contrast Security Community Edition y técnicas manuales de inspección de runtime.

🟣
Sobre IAST en este proyecto: Las herramientas IAST completas (Contrast Security, Seeker, Hdiv) requieren agentes instalados en el servidor. Para esta práctica realizaremos IAST en dos niveles: Nivel A — Contrast Community Edition (agente Node.js gratuito) y Nivel B — Inspección manual de runtime con Node.js Inspector + Chrome DevTools.
🛡️
Herramienta A — Contrast Security Community Edition (Agente Node.js)
Gratis (registro requerido) CLI + Dashboard Web
1
Regístrate en Contrast Security Community
Ve a app.contrastsecurity.com → "Sign Up Free" → crea una cuenta con tu correo universitario. Te dará acceso al panel y a la clave del agente.
2
Instala el agente @contrast/agent en el servidor
Terminal (en el directorio raíz del proyecto)
npm install --save-dev @contrast/agent
3
Crea el archivo de configuración del agente
Crea el archivo contrast_security.yaml en la raíz del proyecto con tus credenciales de Contrast.
Archivo: contrast_security.yaml
# Obtén estos valores desde tu dashboard de Contrast Security api: url: https://app.contrastsecurity.com/Contrast api_key: TU_API_KEY_AQUI service_key: TU_SERVICE_KEY_AQUI user_name: tu-email@dominio.com application: name: SafeCampus-Monitor version: PMV2 server: name: localhost-dev environment: development
4
Inicia el servidor con el agente IAST activo
Terminal
# Ejecuta el servidor con el agente Contrast instrumentado node -r @contrast/agent server/index.js
Si funciona, verás en la terminal mensajes del agente Contrast iniciándose y registrándose en el panel.
5
Navega la aplicación normalmente (el agente observa)
Con el frontend corriendo en localhost:5173, navega la app completa: login, reporte de incidente, ver el dashboard. El agente IAST registra cada operación interna del servidor.
El agente IAST monitoriza en tiempo real:
• Cada consulta SQL ejecutada → detecta queries sin parametrizar
• Cada dato que entra por HTTP y sale hacia la BD → detecta injection flows
• Operaciones con archivos, cookies y headers
• Flujos de autenticación y autorización
6
Revisa el dashboard de Contrast Security
Abre app.contrastsecurity.com → tu aplicación "SafeCampus-Monitor" → tab "Vulnerabilities". Verás los hallazgos detectados durante la navegación.
🔬
Herramienta B — Node.js Inspector + Chrome DevTools (IAST Manual)
Sin instalación Chrome DevTools

Alternativa sin registro externo. Usamos el inspector nativo de Node.js para conectar Chrome DevTools directamente al proceso del servidor y monitorizar su comportamiento en tiempo real.

1
Inicia el servidor con el inspector de Node.js activo
Terminal
node --inspect server/index.js # Verás: Debugger listening on ws://127.0.0.1:9229/...
2
Conecta Chrome al proceso Node.js
Abre Chrome y navega a:
chrome://inspect
Verás tu proceso de Node.js listado. Haz clic en "inspect" → se abre una ventana de DevTools conectada al servidor.
3
Coloca breakpoints en puntos críticos del servidor
En el panel de DevTools del servidor, abre server/index.js y coloca breakpoints (clic en el número de línea) en:
• Línea 32 — const user = await db.get('SELECT * FROM usuarios...') — Ver qué datos llegan a la consulta SQL
• Línea 81 — const { tipo, severidad, jornada... } = req.body — Ver qué datos llegan del frontend
• Línea 96 — await db.run('INSERT INTO incidentes...') — Ver qué se inserta en la BD
4
Ejecuta acciones en la app y observa el flujo de datos
Con el frontend abierto en otra pestaña, intenta:
  • Login con credenciales válidas → observa el objeto user en el breakpoint
  • Login con email ' OR '1'='1 → observa cómo reacciona la query
  • Reportar incidente con descripción larga o con caracteres especiales → observa el req.body
  • Hacer GET /api/incidents sin token usando la pestaña Network de DevTools
🚨
Hallazgo IAST esperado: Al hacer GET /api/incidents sin autenticación, el servidor responde con todos los incidentes. El IAST confirma que no hay middleware de autenticación en esa ruta — vulnerabilidad A01:2021 Broken Access Control confirmada con evidencia de flujo completo.
5
Prueba de autorización horizontal (IDOR)
Verifica si un estudiante puede acceder al panel de autoridades cambiando el token JWT manualmente.
En DevTools → Application → Local Storage:
1. Inicia sesión como Estudiante
2. Abre DevTools → Application → Local Storage
3. Modifica el campo user → cambia "rol":"ESTUDIANTE" por "rol":"AUTORIDAD"
4. Recarga la página

Resultado esperado: Si el router permite acceder al dashboard de autoridad solo por el rol en localStorage (sin verificar en el servidor) → IDOR confirmado. Esto es una vulnerabilidad A01:2021 crítica.

SAST vs DAST vs IAST — ¿Cuál detectó qué?

La siguiente tabla resume el poder de detección de cada técnica aplicada a SafeCampus Monitor:

💡
Conclusión clave de la comparativa: Ninguna técnica por sí sola es suficiente. SAST encontró vulnerabilidades en el código que DAST nunca vería (credenciales hardcodeadas, dependencias). DAST encontró problemas reales de configuración y comportamiento que SAST no puede ver. IAST confirmó los hallazgos más críticos con evidencia de flujo de datos completo, especialmente el problema de control de acceso y la escalada de privilegios.
